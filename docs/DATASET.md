# The Vigil synthetic dataset

Vigil is evaluated on synthetic delivery data. The brief permits this — "run locally with
synthetic delivery data that you document clearly" — and this document is that documentation.

Everything here is generated by `lib/generate/` from a seed. Nothing was collected from a real
fleet, and no real courier, recipient or parcel appears anywhere in it.

---

## Assumptions, not measurements

**This section is first because it is the one that makes the rest of the document
trustworthy.** Every number below was chosen by us. None of it is calibrated against a real
courier fleet, because we do not have one.

| Assumption | Value used | Basis |
|---|---|---|
| Time from collection to delivery | ~20 hours | Plausible next-day Klang Valley shape. Invented. |
| Honest delivery interval | 17 min ± 4 | A courier parking, walking, waiting at a door. Invented. |
| Fraudulent delivery interval (S2) | 20 s | Fast enough to be physically impossible. Invented. |
| Upload latency (`recordTime − eventTime`) | 8–90 s | Plausible mobile upload. Invented. |
| GPS accuracy, good fix | 6–18 m | Consumer GNSS, open sky. Order-of-magnitude realistic; not measured. |
| GPS accuracy, degraded (S6) | 140 m | Underground. Order-of-magnitude realistic; not measured. |
| Battery drain | ~4 pp/hour, monotone within a shift | Plausible for a handset with GPS and radio active. Invented. |
| Doorstep scatter around a geocoded address | ≤ 60 m | Stands in for the difference between a street centroid and a door. Invented. |
| Macro cell offset from an address | ≤ 600 m | Urban macro spacing, roughly. Not surveyed. |
| Fleet dispute rate (background) | ~0% | The background fleet is clean by construction, so the baseline is a floor, not an observation. |
| Fraudster dispute rate (S2) | ~24% | Chosen to be unmistakably out of line. Invented. |
| Parcel declared value | RM 15–450 | Invented. |

**What follows from this.** Detection rates measured on this data describe how the detectors
behave on *our model of* logistics fraud. They are not estimates of real-world performance, and
they should not be presented as such. The distributions are our assumptions; a real fleet's may
differ in ways that change every number.

Two further honesties:

- **The carefulness ladder's monotonicity is a property we assert about the generator, not a
  claim about real attackers.** `lib/generate/generate.test.ts` proves each rung leaves no more
  evidence than the one below it. That makes the attacker-cost sweep a well-formed curve. It
  does not mean real attackers acquire capabilities in that order, or that these five rungs are
  the ones that matter.
- **Addresses are real; everything attached to them is not.** The coordinates are geocoded
  Klang Valley locations. The recipients, parcels and couriers at those coordinates are invented.

## Provenance of the addresses

`lib/generate/data/kl-addresses.json` carries its own provenance in a `source` field, so data
read from it is never of unknown origin:

- `"nominatim"` — geocoded from OpenStreetMap via Nominatim, one request per second with a
  descriptive User-Agent, by `scripts/fetch-addresses.mjs`. **This is what the committed file
  contains.**
- `"curated"` — the script could not reach Nominatim and fell back to hand-checked coordinates.

Address data © OpenStreetMap contributors, ODbL 1.0.

The generator **never** hits the network. A dataset that changes because a third-party geocoder
changed is not reproducible, and reproducibility is the point.

Regenerate the cache with:

```bash
node scripts/fetch-addresses.mjs
```

## The generation model

### The unit is a timeline, not an event

The brief asks for a scenario "from normal activity to a meaningful exception". An isolated
suspicious event cannot show that: there is no normal to depart from, and half the engine
(H1 custody continuity, I3 implied speed, I14 battery) has nothing to compare against.

So the unit generated is a whole shipment:

```
collection → sortation → line-haul departure → line-haul arrival → out for delivery → delivery
```

Each scenario is that timeline with at most one thing wrong, at one leg.

### Warm-up history

Each scenario's courier is given ~14 prior sealed deliveries. Without them the courier is
**cold-start**, every handoff demands an operator co-signature, and S0 cannot demonstrate what
it exists to demonstrate: that ordinary work is accepted without troubling anyone.

### Background fleet

Other couriers' deliveries are written directly to the `events` table as background context.
P2 compares a courier's dispute rate against their peers, and a baseline computed from one
courier is that courier — the comparison would be vacuous. These rows are context, not events
under test; every event belonging to a scenario goes through the real agent.

### Reproducibility

```ts
const world = buildWorld("vigil-2026");
const scenario = buildScenario("S2", { world, rng: makeRng("vigil-2026"), startMs });
```

Same seed, same bytes — asserted by `lib/generate/generate.test.ts`. All randomness comes from
`seedrandom` via `lib/generate/rng.ts`; a purity test fails the build if `Math.random` appears
anywhere under `lib/generate/`.

The **courier keypairs are the one exception** and are deliberately not seeded: they come from
the OS. Private keys should not be reproducible from a public seed.

## The scenarios

| # | Scenario | Injected at | Mechanism | Expected |
|---|---|---|---|---|
| **S0** | Normal delivery | — | nothing | `accept` at every leg, **no co-signature needed** |
| S1 | GPS spoofing | delivery | claimed position ≠ actual; radio environment inconsistent | `flag` — I7 (+I1) |
| **S2** | Batch scanning a condo tower | delivery ×40 | 40 parcels at 20-second intervals; customers complain | `escalate` — P1 + P2, **no I-rule** |
| S3 | Event ID reuse | after delivery | same `eventID`, different parcel | `accept`, then the replay aborts `EVENT_ID_REUSE` |
| S4 | Out-of-scope scan | delivery | EPC outside the courier's mandate prefix | `freeze` — H2 |
| S5 | Clock tampering | delivery | `eventTime` 105 min ahead of `recordTime` | `flag` — I4 |
| **S6** | GPS degradation underground | delivery | 140 m accuracy, cell lost | `accept`, coverage line drops |

S0, S2 and S6 carry the argument.

### S2 and S6 are the pair

Both look, on a dashboard, like a delivery whose location story is odd. One is a courier
defrauding forty customers; the other is a courier in a basement carpark. **In both, every
single event scores zero on all fourteen single-event checks.** A per-event system sees the same
thing in both and can only treat them the same way.

They diverge on axis 2, and only there:

- **S2** is caught by **P1** (a delivery rate no one can walk) and **P2** (the customers say the
  parcel never came). P1 is a property of the **set**; P2 is an outcome that **arrives later**.
  Neither exists inside any single event.
- **S6** is left alone, because a degraded GPS fix *reports its own uncertainty* and a missing
  cell observation is *missing* rather than contradictory. The location rules return
  `not_evaluated`, the coverage line drops from 13/14 to 10/14, and the operator is told how
  much evidence there actually was.

**A fraudster can fake WHERE. They cannot fake HOW FAST, or WHETHER THE CUSTOMER GOT IT.**

### Why S2 is a condo tower and not a van

The original design (`track idea.md` §8) had the courier park a van and scan parcels addressed
across the neighbourhood. Traced against the engine, **that scenario cannot be a signature
case**: scanning from one spot puts every scan hundreds of metres to kilometres from its
recipient address, so I10/I11 fire on *every* event. Moving the claimed positions to the
addresses to fix that makes consecutive scans imply impossible speeds, so I3 fires instead.
Either way axis 1 catches it, and S2 stops being the case only the pattern axis can see.

The condo tower keeps every event genuinely clean while the *shape* stays wrong. This was found
by tracing the scenario against the built engine, before running it.

## The `vigil:` extension fields

Mock-location flags, radio observations and integrity attestations are not in the GS1 Core
Business Vocabulary. They live under a `vigil:` namespace inside `sensorElementList`, which is
where EPCIS 2.0 provides for user extensions. `vigil:courierId` sits at the event root.

Everything below is a **signal**, never a **judgement**. Nothing here says "fraudulent"; the
engine decides that by finding contradictions across signals.

| Field | Meaning | Used by |
|---|---|---|
| `vigil:courierId` | The courier the scan **claims** to come from. Unverified by construction. | H2, H3, I6 |
| `deviceId` | Hardware id of the scanning handset | I6 |
| `gps.point` | Reported position, with `accuracyMeters` | I1, I2, I3, I10/I11 |
| `gps.fixTime` | When the fix was taken | — |
| `gps.speedMps` | Device-reported speed | I2 |
| `gps.mockLocationProvider` | OS reports the position came from a fake-location app | I7 |
| `cell` | Serving cell (`mcc`, `mnc`, `lac`, `cellId`) | I1 |
| `wifi[]` | Visible access points (`bssid`, `rssiDbm`) | I1 |
| `motion` | Accelerometer summary over the preceding window | I2 |
| `integrity.attestationSource` | **Always `"mocked"` in this dataset** | I8 |
| `integrity.verdict` / `rootDetected` / `appTampered` | Simulated Play Integrity output | I8 |
| `battery.levelPercent` / `charging` | Handset battery | I14 |
| `pod.photoSha256` / `photoExifCaptureTime` | Proof-of-delivery photo hash and EXIF time | I9, I12 |
| `pod.otpVerified` / `signatureSha256` | OTP and recipient signature | I12 |

**`attestationSource` is always `"mocked"`.** The prototype simulates Play Integrity, and a
simulated attestation that is indistinguishable from a real one inside our own dataset would be
precisely the forgery this project claims to detect.

## The holdout split

`lib/generate/split.ts` partitions a set deterministically from an item's own key:

```ts
const { tune, report } = partition(runs, (r) => r.id, "experiment-seed");
```

Thresholds are tuned on `tune` and reported on `report`. Thresholds tuned on the data they are
reported against measure how well they were tuned. The split is a pure function of the key, not
of position, so adding runs does not reassign the ones already placed.

## The carefulness ladder

`lib/generate/carefulness.ts` describes what the fraudster had to **obtain**, not which detector
it defeats:

| Level | Capability |
|---|---|
| 0 | A mock-location app from the app store |
| 1 | A rooted handset, so the OS stops reporting the mock provider |
| 2 | A patched build that passes attestation and forges the radio environment |
| 3 | The above, plus a synthesised accelerometer trace and battery curve |
| 4 | The above, plus a recipient who agrees not to complain |

Level 4 is the boundary written into Known Limitations: a patched device operated by someone
colluding with the recipient is out of this architecture's reach on a single event.

## Anti-circularity

**The generator does not import the detector's thresholds.** `lib/purity.test.ts` fails the
build if any module under `lib/generate/` imports `lib/engine/thresholds`,
`lib/pattern/thresholds`, `lib/gate/thresholds`, or names a threshold constant.

A generator that reads `p1.maxDeliveriesInWindow` to decide how fast the fraudster scans is not
producing a fraudster; it is producing something shaped to trip a rule. A detection rate
obtained that way is circular — it would stay high if the rule were nonsense, because the data
was built around the rule.

So the generator emits **behaviour** ("one parcel every twenty seconds", "the courier is in a
basement carpark", "the recipient agrees not to complain") and the detectors compute statistics
over it. If a threshold moves, the generator does not.
